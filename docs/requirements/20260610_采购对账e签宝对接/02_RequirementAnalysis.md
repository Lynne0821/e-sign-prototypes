# Part A · 需求识别 (Identification)

### A1. 用户故事 (User Stories)
- **采购员发起签署**：作为采购员，我想要系统能自动从金蝶拉取“已审核”的采购单并生成 PDF，以便我能一键向供应商发起 e签宝电子签署。
  - *AC*：必须只拉取“已审核”状态的订单；系统需按模板样式准确组装 PDF；点击发起后，调用 e签宝接口成功并扭转单据状态为“签署中”。
- **结算专员发起签署**：作为财务/结算专员，我想要系统自动从携客云拉取“已确认”状态的对账单并生成 PDF，以便我能发起 e签宝对账单的电子签署。
  - *AC*：拉取的数据中“对账含税金额”校验等于“出货-退货+费用”；发起后能正确传达至配置好的供应商联系人。
- **配置与管理**：作为运营人员，我想要在交付系统中配置供应商映射与签署人联系方式，以便发起时系统能根据默认配置自动找准接收方。
  - *AC*：提供供应商与联系人/手机号映射关系管理界面；支持针对不同单据类型设置默认内部用印组织。
- **状态与文件归档**：作为交付系统的使用者，我想要系统能接收 e签宝的签署回调，以便自动更新单据状态为“已完成”并归档生效的 PDF。
  - *AC*：签署完成、拒签或撤销等状态均需被监听更新；生效文件支持在单据详情页在线预览和下载。

### A2. 功能清单 (Feature List)
- `单据集成 -> 金蝶采购单同步 (P0)`：拉取金蝶“已审核”采购单数据。
- `单据集成 -> 携客云对账单同步 (P0)`：拉取携客云“已确认”对账单数据。
- `模板服务 -> 采购单/对账单 PDF 渲染组装 (P0)`：依据上游数据按模板规则生成待签署 PDF 文件。
- `签署配置 -> 供应商签署人及内部印章配置表 (P1)`：维护供应商名称与联系人/电话对应关系。
- `e签宝对接 -> 签署任务发起接口 (P0)`：向 e签宝推送文件及签署方信息并创建签署任务。
- `e签宝对接 -> Webhook 状态及文件回传监听 (P0)`：处理回调并持久化存储 PDF。
- `单据管理 -> 签署状态可视化与流转 (P1)`：列表展示（待发起、签署中、已签署、拒签/作废），提供重新发起、手动作废功能。

### A3. 业务规则 (Business Rules)
- **前置准入**：只有当上游状态满足（采购单=已审核，对账单=已确认）且配置表中找得到对应供应商时，才允许“发起签署”。
- **金额规则（强校验）**：对账含税金额 = 货明细含税汇总 - 仓退明细含税汇总 + 费用含税，组装模板时需验证数据配平，否则阻断并报警。
- **签署通知规则**：交付系统仅做发起动作，审批和用印管控等流转全部交由 e签宝平台内部规则处理。

### A4. 潜在异常与边界 (Edge Cases)
- **配置缺失**：单据中的供应商在配置表中不存在，或联系方式为空时，需做前端强阻断拦截。
- **回调丢失/超时**：e签宝回调异常，导致交付系统一直卡在“签署中”。（需提供手动同步/查询签署状态的功能兜底）。
- **供应商拒签**：供应商在 e签宝中因金额异议点击拒签，需能更新状态至交付系统，并允许专员调整上游数据后**重新拉取生成发起**。

# Part B · 影响面与风险 (Impact Analysis)

### B1. 逻辑闭环性审计 (Logical Integrity)
- **数据流闭环**：金蝶/携客云（数据源） -> 交付系统（渲染与发起） -> e签宝（执行签署） -> 交付系统（归档）。整体数据主线完整，但在“单据被退回/拒签”的逆向分支上，需要交付系统内有明确的重置或重新流转入口。
- **联系人数据前置**：必须保证发起前，采购已经在线下收集好并录入了供应商的对接人和手机号，否则会卡在“无签署接收方”。

### B2. 数据一致性与链路影响 (Impact Mapping)
- **上游链路冲击**：无直接冲击，因为仅作为下游获取“终态”进行组装。但若未来金蝶或携客云自身也要存储电子版合同，可能需要增加“已生效 PDF 回传至金蝶/携客云”的接口。
- **财务与对账链路**：对账单完成电子签署代表财务上确认可付款，需要确保交付系统的“已签署”状态与实际打款系统间的对齐。

### B3. 风险评估 (Risk Assessment)
- **技术可行性风险 (低)**：e签宝的基于文件的签署和模板化传参是标准 API，技术风险可控，核心在于交付系统的 PDF 渲染画板能否高保真还原当前的 Excel 样式（尤其是带分页的超长送货明细）。
- **配置维护成本 (中)**：供应商的签署人和联系方式为系统配置，如果供应商人员发生变动，可能会导致发送到错误的手机号，需要在页面加入便捷的临时修改签署人功能。

### B4. 冲突提醒 (Conflict Alerts)
- **上游单据撤回机制缺失（待 PM 确认）**：如果“金蝶已审核的订单”在发起 e签宝签署后，被金蝶财务人员**反审核甚至修改了金额**。此时 e签宝里的任务应如何处理？（**建议：交付系统应订阅上游撤销消息，或上游禁止对正在“签署中”的单据反审核**）。
